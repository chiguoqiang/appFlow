## 断点日志

> 格式：`[阶段] 断点描述 → 处理方式 → 契约/模板改进建议`

- [立项] 用户回复待澄清问题时未直接给出 N 的具体数值（复述了问题项）→ 按建议值采纳并在简报「已澄清记录」写明来源 → **改进建议：关卡提问应把「建议值」放在问题首句，让确认动作零歧义（未来 Portal 用单选代替自由回答）**
- [规划] weeklyN 习惯的 streak 语义存在口径歧义（天数 vs 周数）→ 规划 Agent 直接定案（连续周数）并记录决策 → **改进建议：PRD 模板第 5 节增加「统计口径」显式小节，强制此类定义进契约**
- [设计] **Figma 写入通道断点**：本会话仅有 Figma MCP 读取工具（get_figma_data/download_images），无画布写入/驱动 Figma Make 的通道 → 「驱动 Figma AI 生成」动作在 P0 由**用户人工代执行**：复制设计需求书第 2-4 节 → Figma Make/First Draft 生成 → 把文件链接回传 → 设计 Agent 用 MCP 读回校验 → **改进建议：P1 把「需求书 → Figma Make 提示词」的转换固化为脚本/模板，减少人工翻译损耗；P2 探索 Figma 插件桥接自动化**
- [设计] 团队级 Figma 组件库/Variables 不存在（前置资产缺失）→ 设计 Agent 改为「项目内自建轻量 token 集」（需求书第 2 节为唯一权威值），Figma 侧按值生成 → **改进建议：新增前置检查项——流水线启动前检测组件库资产，无则自动切换「自建 token」模式（本次已按此执行，模板 02 需把该分支显式化）**
- [设计] **Figma MCP OAuth 令牌过期（403 Token expired）**，用户回传的 Figma Make 文件无法读回校验 → 降级执行：三件套产出结构化部分（tokens JSON 以需求书为权威），node ID 与截图标记「待补」；开发不被阻塞，Figma 令牌修复后回填并补做校验 → **改进建议：① 流水线前置健康检查应包含「Figma MCP 连通性探测」而非假设可用；② 三件套模板的 node ID/截图字段需要允许 `pending` 状态，且「待补回填」需在 pipeline-state 有追踪（否则易被遗忘）**
- [开发] **规范体系未落地到项目内**：开发 Agent 定义要求「按 flutter-dev-playbook / AGENTS.md 三级 Rules」执行，但 `demo-app` 无根 `AGENTS.md` 与 `.github/skills/.../rules`（规范库在 `~/.agents` 个人级）→ 本次按默认约定（分层目录、analyze/test DoD）执行并汇报 → **改进建议：P1 的工程初始化步骤必须显式包含「规范体系落地」（复制 rules + 生成 AGENTS.md 索引），否则"规范驱动"只是口头承诺，P2 换 Agent 就漂移**
- [开发] **设计 tokens 覆盖不全**：热力图格子圆角（8）、空态图标灰均无对应 token，开发只能硬编码或派生 → **改进建议：设计阶段增加「token 覆盖自检」——把逐页指令里出现的所有尺寸/颜色值反查 token，缺失即补，避免开发阶段被迫越界**
- [开发] **热力图 5 行契约缺陷**：需求书/PRD 写「7 列×5 行」，但 30 天 + 起始偏移最坏需 36 格（35 格容量溢出）→ 开发改为动态行数并在自测报告声明偏差 → **改进建议：涉及"天数/网格容量"的规约必须写成公式（如 rows = ceil((leading + days) / 7)），不要写死行数**
- [开发] 测试捕获真实缺陷：`ListTile` 置于带背景的 `Container` 内触发框架断言（ink 不可见）→ 为 `AppCard` 加内层透明 `Material` 修复 → **说明：组件测试在 P0 就抓到了渲染层问题，证明「测试阶段前移」有效，应固化为开发 Agent 的 DoD（先写组件测试再接页面）**
- [测试] **测试 Agent 独立用例发现 4 个开发自测未发现问题（含 1 个高严重度）**，其中开发自测报告 K-4 明确断言「done>due 不可能」，实为**断言错误**而非漏测 → **改进建议：开发 Agent 定义增加规则「凡断言『不可能发生』必须附构造性证明，否则标注为假设待验证」；测试 Agent 定义增加「专攻开发声称的不可能性」这一取证策略（已在本轮生效）**
- [测试] **测试 Agent 缺少截图能力（双侧受阻）**：golden master 侧（Figma 令牌过期）+ 运行时侧（`simctl` 无法点击驱动多页）→ 导致 TS-12 UI 对比只能人工核对 PG-01，PG-02/03/04 完全无运行时截图 → **改进建议：P1 首个交付项就应包含 `integration_test` 四页自动截图脚本（同时产出运行时截图与 golden master 基线），这是验收自动化的前置依赖**
- [测试] **「有条件通过」判定依据不足**：模板未定义「高严重度缺陷是否允许放行」的硬门槛，本次由测试 Agent 自行裁定为「不通过」→ **改进建议：测试报告模板第 1 节加入质量门硬规则（如：高严重度未修复 = 自动不通过），把判定从主观改为规则**

### 阶段性结论（测试/验收完成后补记）

**P0 成功指标达成**：发现并记录 **15 条断点**（远超"零断点"的伪成功），
其中 6 条属系统性缺陷（非个案），已转化为模板改进建议表。

**最关键的发现：「声明依赖 ≠ 装配依赖」**
流水线各 Agent 定义里都写了「按 XXX 规范/资产执行」，但没有任何环节负责**把资产装配到位**
（规范体系文件、Figma 连通性、截图工具链）。这导致 3 个阶段分别踩坑。P1 必须新增
「启动资产装配检查」这一步——这是本次 P0 最大的架构级收获。

**第二大发现：独立测试的价值被量化**
开发自测 65 项全绿，测试 Agent 17 项独立用例找出 4 个缺陷（1 高严重度），命中率 ~24%。
证明「测试 Agent 不复用开发用例」这条设计原则必须保留（若复用开发用例，命中率会趋近 0）。

**第三：降级预案让流水线不因工具故障停摆**
Figma 令牌过期 → tokens 先行；截图缺失 → 人工核对 + 判定上限 ⚠️。全程无阻塞。
但代价是遗留 L-04（UI 基线缺失）——说明降级必须**同时登记回填任务**，否则会被遗忘。
